Written 2026-09-29 on top of commit `4889140`, **before** any label-blind question set exists, and before
any router is scored on the second pool. It is frozen by the commit that adds it. If it is pushed, the

**What has already been seen (disclosure).**

- Jev's success-prediction AUROC for deepseek-v3-0324 and gpt-5-chat is reported in

## Part 1. X2: label-blind question sets

### Question

Does the few-label advantage survive when the 13 questions come from a generator that has seen no
prompts, no outcomes and no model names, instead of from the author's dev-split iteration?

### Generation (frozen)

- **Model:** `claude-sonnet-5` via the Anthropic API, default sampling settings.
- **Samples:** three independent samples of the prompt below, generated once. They are called Q-blind-1,
  -2 and -3.
- **Allowed input:** the prompt text below only. No benchmark prompts, no v1 questions and no results are
  shown.

Prompt (verbatim):

> A router must decide, before any language model answers, whether a given language model will answer a
> user request fully and correctly. It sees only the request: a conversation, possibly including an
> agent's earlier steps. The requests come from a mix of competition mathematics, programming problems,
> graduate-level science questions, general multiple-choice knowledge questions and software-engineering
> issues.
>
> Write exactly 13 yes/no questions about the request that a careful reader could answer from the request
> text alone, and whose answers would help predict whether a language model succeeds. Do not mention any
> specific model, company or benchmark. Return a JSON object mapping a short snake_case id to each
> question.

**Format check** (applied before any answering):
- exactly 13 questions;
- each answerable yes/no;
- no model, company or benchmark names;
- each ≤ 50 words.

A sample that fails is regenerated **once**, and the failure is logged. If the regeneration also fails,
use it with the offending questions dropped and report that.

### Answering and evaluation (identical to v1 unless stated)

- **Answerer:** Jev `jev-1.13.0`, each question sent as a Noul with the question as `instructions`, one
  fan-out request per prompt. The returned `model` field is logged.
- **Router-visible text:** as in `configs/llmrouterbench_test.yaml` (Jev `max_chars` 16,000).
- **Prompts:** all 4,934 LLMRouterBench prompts, so label draws and the test split match experiment T.
- **Heads:** per-model logistic regression, C = 1.
- **Splits:**
  - seed-42 test split with design-seen prompts moved to train (1,328 test prompts);
  - label seeds 42, 999, 2024, 2025, 3407;
  - k ∈ {10, 25, 50, 100, 200, all}.
- **Metric:** within-category AUROC of P(cheapest model suffices), the same categories rule as the paper.

### Endpoints

- **Primary:** at k = 25, the mean over Q-blind-1..3 of (Q-blind minus `bge_knn`), with a hierarchical
  bootstrap (2,000 replicates) resampling question sets, label seeds and test prompts (stratified by
  category).
  - **Success:** 95% CI lower bound > 0.
  - `bge_knn` is the primary baseline fixed by the pre-registered rule in `notes/preregistration.md`.
- **Secondary** (reported whatever the result):
  1. Q-blind (mean over sets) minus Q-author (v1) at every k, two-sided.
  2. The primary contrast at every k and for each set separately.
  3. The same contrast on the 9 unseen targets of experiment T at k = 25 (mean over targets and sets).
  4. Semantic overlap: for each Q-blind question, the closest v1 question (by bge-large cosine), reported
     as a table.

**Reading, fixed in advance:**

| Result | Reading |
|---|---|
| Q-blind ≈ Q-author (two-sided CI spans 0) and the primary succeeds | Design supervision is not the explanation |
| Primary succeeds, but Q-blind < Q-author | Part of the gain is expert question design; report both |
| Primary fails | The few-label advantage depends on the author's questions; the paper must say so |

**Budget:** Jev ≤ $3 for three sets over 4,934 prompts; generator < $1; hard cap $6.

## Part 2. A second model pool with more headroom

### Why

On the original pool the oracle beats the strong model by only +0.049 (train split), and no router beats
always-mid. We test whether few-label success prediction turns into routing gains when the pool has more
room.

### Selection rule (frozen; train split only)

Among single named models with outcomes for all 4,934 prompts (excluding `openrouter`), consider every
pair (cheap, strong) with:
- mean cost(cheap) ≤ mean cost(strong) / 3;
- train accuracy(cheap) ≤ train accuracy(strong).

Choose the pair with the largest train-split oracle gain over the strong model; ties go to the larger cost
ratio. The 2026-09-29 scan (`scripts/headroom.py`) gives:
- **cheap = deepseek-v3-0324, strong = gpt-5-chat**;
- train accuracy 0.680 and 0.680;
- oracle 0.771 (+0.091);
- mean cost $0.0012 vs $0.0066.

### Evaluation

- **Setup:** the same test split, label seeds and cached Jev answers (v1 questions), with per-model heads
  for the two models. Baselines and the always-cheap / always-strong / random-at-matched-cost references
  are unchanged. Cost is the release's per-prompt cost; router cost is added as in the paper.
- **Operating point:** the threshold is chosen on the k labeled prompts only, to maximize labeled-set
  quality subject to mean cost ≤ the strong model's mean cost. It is applied unchanged to test.
- **Primary endpoint:** at k = 25, test quality of `jev:features` at that operating point minus the best
  single model's test quality, with a paired bootstrap over label seeds and test prompts.
  - **Success:** 95% CI lower bound > 0 (routing beats both single models).
  - Also reported: the cost difference to the strong model.
- **Secondary:**
  - the same at k = all;
  - `bge_knn` and `tfidf_logreg` at the same operating-point rule;
  - random at matched cost;
  - within-category AUROC for each model;
  - AIQ(log) against the zero router.
- **Headroom analysis (§4 item 2 of the plan; exploratory by design):** on both pools, simulate
  predictors of given within-category AUROC (Gaussian scores with matched base rates) and report the
  AUROC needed to beat the best single model at matched cost.

**Reading, fixed in advance:**

| Result | Reading |
|---|---|
| Primary succeeds | Few-label success prediction produces routing gains when the pool has headroom; the original null is a pool property |
| Primary fails, text routers also fail | Success-prediction AUROC in this range is not enough to route profitably even with headroom; report as a strengthened null |
| Primary fails, a text router succeeds | Contradicts the paper's framing; report prominently |

**Budget:** $0 (all offline from the cache and the release).

## Reporting rules

- All results are reported, including failures.
- Failed Jev calls are retried, never scored. Anything still failing is imputed at 0.5 at test, dropped
  from training, and reported if > 1%.
- No question set is edited after its answers are requested.
